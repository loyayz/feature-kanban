# Feature Lifecycle Kanban 设计规格

## 目标

Feature Lifecycle Kanban 是一个 Windows 优先、本地单用户的 Codex 生命周期看板。每个新的 `feature-lifecycle` 本地流程对应一张卡片；AI 在关键节点通过本地 HTTP API 上报当前快照，看板只展示和导航，不推断聊天内容、不编排 AI、不管理 Git 或 worktree。

首版必须同时支持 Codex 与 Claude 使用同一份跨工具 `feature-lifecycle` Skill。Codex 提供深度桌面集成；Claude 在看板服务已运行时调用相同 API，服务不可用时只记录本地同步失败。

## 非目标

- 不支持多人、局域网、云端或跨设备同步。
- 不读取或操作 Git、分支或 worktree；分支名只是 AI 上报的只读元数据。
- 不监听聊天并自动推断进度，不上传 AI 输出、命令或测试日志。
- 不保存通用事件时间线、阶段历史、评审历史或同步事件历史。
- 不提供任务查重。标题、项目名或分支相同的新生命周期文档仍创建新卡片。
- 不允许用户拖动卡片或从 UI 修改生命周期阶段。
- 不提供 CLI。Skill 直接调用 REST API，也不负责启动或停止服务。
- 不保证 Claude 会话可以深度跳转；真实会话 ID 或链接不可用时仍允许上报。
- 不提供 WebSocket、远程控制 AI、内置 AI Chat、甘特图或工作流编辑器。

## 领域术语

- **Lifecycle Flow（生命周期流程）**：由一个生命周期文档、一个 `cardId` 和一系列阶段快照标识的本地需求流程。它是业务上的跟踪单元。
- **Card（卡片）**：Lifecycle Flow 在看板中的当前投影，不是独立任务，也不保存阶段历史。
- **Project（项目）**：按原始仓库根目录末级名称聚合的显示分组，不是仓库路径或 Git 身份。
- **AI Session（AI 会话）**：某个 AI 工具接管 Lifecycle Flow 的一次执行上下文；卡片保留这些会话记录，但它们不构成通用事件时间线。
- **Managed Codex Instance（托管 Codex 实例）**：由 Feature Kanban 快捷方式启动、开放回环 CDP 并受启动器生命周期监督的官方 Codex 桌面进程。
- **Service Ownership（服务所有权）**：启动器只停止自己创建的看板服务；健康检查发现并复用的手工服务不归启动器所有。

## 核心产品语义

### 一项需求一张卡

新的本地生命周期流程先创建生命周期文档，再生成一个 UUID `cardId` 并写入该文档，然后调用 `POST /api/cards`。同一生命周期文档恢复时沿用原 `cardId`；明确重新开始并创建新生命周期文档时生成新 `cardId`。

`POST /api/cards` 的请求体包含客户端生成的 `cardId`。首次创建返回 `201`。网络重试使用相同 `cardId` 时返回已有卡片而不重复创建，并且不覆盖已有快照或改变归档状态；如果相同 ID 对应的项目名或生命周期文档路径不同，返回 `409`。调用方在确认卡片存在后使用 `PATCH /api/cards/{cardId}` 上报当前完整快照。PATCH 采用最后写入者覆盖，不使用乐观版本号。

服务不要求阶段单调前进，因为 `feature-lifecycle` 在变更面越界或评审发现架构问题时可以合法返回方案设计。并发会话中最后到达的合法 PATCH 可以覆盖较新的业务进度，包含阶段回退；这是用户选择最后写入者覆盖后接受的行为。服务只校验快照结构，不操作 Git 验证阶段真实性，`completed` 由 Skill 在成功整合 base 后上报。

卡片标题是 `<feature-slug>`，不包含生命周期文档文件名开头的 `YYYY-MM-DD-` 日期或 `.md` 扩展名。项目名由 AI 从生命周期启动时记录的原始仓库根目录 `<repo-root>` 的末级目录名取得，而不是从 linked worktree 目录名取得。服务仅以该名称识别项目；不同绝对路径下的同名目录会合并到同一项目，这是首版接受的限制。

### 生命周期阶段

卡片阶段按固定顺序排列：

1. `initializing` — 流程初始化
2. `designing` — 方案设计
3. `requirements_review` — 需求评审
4. `implementation_planning` — 实现计划
5. `implementing_and_reviewing` — 编码与评审
6. `finalizing_branch` — 分支整理
7. `awaiting_integration` — 待整合
8. `completed` — 已完成

只有 feature 分支成功整合到 base 后才能进入 `completed`。分支已经验证但用户拒绝或暂不整合时，卡片保留在 `awaiting_integration`。

`waiting_for_user` 与 `blocked` 是可叠加标记，不改变主阶段。看板 API 不可用不是卡片标记，因为失败时无法可靠写入看板；它只记录在生命周期文档中，下一次成功上报完整快照时清除本地失败记录。

### 结构化阶段内进度

卡片只保存当前进度，不保留旧值。进度是按阶段区分的结构化对象：

- 初始化：`creating_worktree`、`creating_lifecycle_document`、`ready`。
- 方案设计：`clarifying`、`comparing_approaches`、`writing_spec`、`complete`。
- 需求评审：`reviewing`、`updating_spec`、`complete`。
- 实现计划：`planning`、`complete`。
- 编码与评审：当前活动为 `coding`、`validating`、`reviewing` 或 `fixing`；可附带实现批次、评审轮次和连续干净轮数。
- 分支整理：`quality_gate`、`squashing`、`rebasing` 或 `verifying_final_state`。
- 待整合：`waiting_for_user` 或 `integration_declined`。
- 已完成：固定为 `integrated`。

阻塞时可包含一条当前阻塞原因；这仍是当前快照，不是历史记录。服务端按阶段校验进度类型，拒绝阶段与进度不匹配的请求。

## 数据模型

SQLite 只保存当前业务状态和会话历史，不保存事件表。

### Cards

每张卡包含：

- `id`：AI 生成的 UUID。
- `project_name`：项目目录名，也是项目唯一标识。
- `title`：生命周期文档文件名去掉扩展名。
- `stage` 与阶段匹配的 `progress`。
- `waiting_for_user`、`blocked` 和可选阻塞原因。
- `ai_tool`：当前工具名，首版识别 `codex`、`claude`，协议允许其他非空工具名。
- `branch`：当前分支名。
- `lifecycle_document_path`：AI 上报的生命周期文档路径。
- `active_session_record_id`：当前活动会话记录。
- `archived`。
- `last_synced_at`：最近一次 AI POST 创建或 PATCH 快照的时间。
- `created_at`、`updated_at`；归档只改变 `updated_at`，不改变 `last_synced_at`。

不保存 worktree 路径、原始用户请求或需求摘要。项目列表由未归档及已归档卡片的 `project_name` 去重得到，不建立项目配置或项目路径表。

### AI sessions

卡片保留全部执行会话，并且只有一条为当前活动会话。每条记录包含：

- 客户端生成的 `session_record_id`。
- `card_id`。
- `ai_tool`。
- 可选真实 `external_session_id`。
- 可选跳转 URI。
- `started_at`、`last_seen_at`。
- 当前活动标记。

AI 能取得真实会话 ID 时使用它稳定识别会话；无法取得时仍生成 `session_record_id`，记录工具和接管时间。生命周期文档保存当前 `session_record_id`，使没有真实 ID 的同一会话可以继续更新，而新的接管会话会创建新记录。

工具变化或新会话接管时不覆盖旧记录。卡片的当前 `ai_tool` 与活动会话一致；工具切换历史由会话列表自然体现，不单独创建活动事件。

## 本地服务

一个 Node.js + TypeScript 进程提供四项能力：

- REST API。
- SSE 变更通知。
- SQLite 持久化。
- 编译后的 Angular 静态资源。

默认监听 `127.0.0.1`，默认地址由应用配置定义，并允许源码运行时通过环境变量覆盖。服务拒绝非回环绑定，写 API 不使用令牌。浏览器请求执行严格的 `Origin` 与 CORS 限制，但任何本机进程仍能调用 API；这是用户明确接受的首版安全边界。

数据、运行锁和日志位于用户主目录的 `.feature-kanban`，Windows 示例为 `C:\Users\<用户名>\.feature-kanban`。源码仓库和安装目录不保存业务数据库。

### REST API

首版 API 包含：

- `GET /api/health`：返回产品标识、版本和服务所有权信息。
- `GET /api/projects`：返回按项目名聚合的项目及卡片数量。
- `GET /api/cards`：按项目名、AI 工具和归档状态筛选；`project=all` 返回全部项目。
- `GET /api/cards/{cardId}`：返回单张卡及会话列表。
- `POST /api/cards`：创建卡片；相同卡片 ID 的同一流程重试返回已有卡片但不覆盖快照。
- `PATCH /api/cards/{cardId}`：用最后写入者覆盖当前生命周期快照并自动取消归档。
- `PATCH /api/cards/{cardId}/archive`：仅由 UI 设置归档状态。
- `GET /api/events`：SSE 连接。

每次创建、生命周期更新或归档都在 SQLite 事务提交后广播轻量事件。请求校验失败返回 `400`，卡片不存在返回 `404`，`cardId` 与流程身份冲突返回 `409`，数据库失败返回 `500` 且不广播事件。

### SSE

SSE 只承担“已打开的看板及时知道哪张卡发生变化”的职责。事件包含事件类型和 `cardId`，不包含日志、历史或修订号。

Angular 按 `cardId` 合并 150ms 内的连续通知，对每张受影响卡只调用一次 `GET /api/cards/{cardId}`。断线后依赖浏览器自动重连；重新连接时执行完整列表加载，不补发历史事件。

## Angular 看板

### 布局

看板采用经典横向生命周期流水线。左侧固定项目列表，首项为 `All`，其后是按项目名排序的项目。顶部提供 AI 工具筛选和归档视图入口。主体包含八个固定阶段列，允许横向滚动。

卡片展示标题、项目名、当前 AI 工具、结构化阶段内进度、等待或阻塞标记、分支摘要及最后同步时间。点击卡片打开右侧详情面板，展示完整分支、生命周期文档路径和全部 AI 会话；路径与无法跳转的会话 ID 支持复制。

用户可以查看、筛选、打开会话和归档卡片，但不能拖动卡片或修改阶段。任何阶段均可归档；同一流程下一次成功执行 `PATCH` 上报时自动取消归档并重新显示。

### 阶段推进动画

当已经显示的卡片收到新快照且阶段发生变化时，卡片执行“轻微抬起、滑行、落位”：短暂提高阴影与缩放，沿列方向移动到目标列，目标列短暂高亮。动画不显示文字提示。

同一张卡 150ms 内的连续 SSE 通知只播放一次从旧快照到最终快照的动画。首次加载、项目或工具筛选变化、归档视图切换、SSE 重连后的完整刷新均不播放迁移动画。系统启用“减少动态效果”时取消位移动画，仅更新布局和焦点。

视觉风格采用与 Codex 桌面应用协调的中性界面，强调清晰层级、紧凑卡片和可读状态，不复制或修改 Codex 自身前端资源。

## Codex 桌面集成

### Windows 托管启动器

Windows 安装器创建一个新的“Codex”快捷方式，名称和图标保持用户熟悉的 Codex 入口，但不修改官方应用文件或原有快捷方式。

启动器遵循以下规则：

1. 使用单实例控制。重复点击由启动器托管的 Codex 时激活已有窗口，只保留一套注入器和看板服务。
2. 使用官方默认用户配置，不创建独立 profile，因此现有登录、项目和会话保持不变。
3. 如果检测到通过普通官方入口启动且未由本启动器托管的 Codex，直接弹窗报错，建议用户关闭原 Codex 后从新快捷方式启动；不自动关闭进程，也不启动第二个实例。
4. 如果看板健康端点不存在，启动器启动本地服务并记录所有权；如果检测到有效的手工 `npm start` 服务则复用，但不取得其所有权。
5. 启动官方 Codex 时仅在回环地址开放 CDP，等待目标渲染器后注入侧边栏入口、iframe 与消息桥。
6. 托管的 Codex 完全退出后停止注入器，并且只停止由本次启动器创建的服务。手工独立服务不随 Codex 关闭。

安装版固定使用两个回环 TCP 端口：看板 REST/SSE 服务使用 `46171`，Codex CDP 使用 `46172`。启动器在创建进程前分别检查端口：`46171` 上若是合法 Feature Kanban 健康端点则按既有所有权规则复用，若是其他监听者则直接报出端口和用途；`46172` 已被占用时不启动 Codex，并提示用户释放端口。源码模式的 `npm start` 仍可通过 `FEATURE_KANBAN_PORT` 覆盖看板端口；安装版忽略该开发环境覆盖，保证注入页、健康检查和服务端使用同一固定地址。

CDP 在运行期间允许受信任的本机进程调试 Codex，是用户已经批准的运行安全影响。启动器不修改 Codex 的安装文件、私有数据文件或打包资源。

### 注入与导航桥

注入层在 Codex 原生侧边栏增加 Feature Kanban 入口，并在主区域加载同源本地 Angular 页面。它负责 iframe 显示、CSP 适配、渲染器替换后的重新注入以及严格校验的 `postMessage` 桥。

Angular 请求打开 Codex 会话时，消息桥使用保存的真实 thread ID 调用 Codex 当前可用的原生路由能力。没有真实 ID 或当前 Codex 不支持导航时，详情面板提供复制 ID，不伪造成功跳转。Claude 使用上报的可选 URI；没有 URI 时同样只复制 ID。

## Feature Lifecycle Skill 集成

仓库交付一份完整的跨工具 `feature-lifecycle` Skill 源文件。Windows 安装器只在 `%USERPROFILE%\.agents\skills\feature-lifecycle` 安装或更新这一份 Skill；Codex、Claude 及其他支持 `.agents\skills` 发现约定的 AI 工具共享该目录。安装器不得向 `.codex\skills` 或 `.claude\skills` 部署副本，仓库同时提供该唯一目录的手工安装说明。

自动安装覆盖同名 Skill 前先创建备份并记录安装内容哈希。卸载时，只有目标内容仍等于安装器部署版本才删除并恢复备份；如果用户之后修改过 Skill，则保留当前文件和备份，并给出手工恢复说明。Skill 安装失败不阻止看板主体安装，但安装器必须显示失败路径。

Skill 在生命周期关键节点执行：

- 新流程创建生命周期文档后生成 `cardId` 和 `session_record_id`，先写入文档，再执行 `POST /api/cards`。
- 恢复同一文档时沿用已有 ID；AI 工具或真实会话改变时创建新的会话记录并将其设为活动会话。
- 进入主阶段、阶段内进度改变、等待用户、阻塞、恢复和最终整合成功时执行 `PATCH` 完整快照。
- Stage 4 上报实现批次、当前活动、评审轮次和连续干净轮数。
- Stage 5 完成最终分支验证后进入待整合；只有 base 成功整合后进入已完成。
- 每次成功上报更新文档中的同步状态；失败时记录错误摘要并继续本地生命周期，Skill 不启动服务。

生命周期文档至少记录 AI 工具、Card ID、当前 Session Record ID、看板同步状态、分支和本身路径。卡片只接收分支与生命周期文档路径，不接收 worktree 路径。

## 独立运行与安装

源码模式提供 `npm start` 独立启动同一个 Node 服务，以及开发、构建、检查和 Windows 打包命令。Skill 不调用这些命令。

Windows 安装器采用每用户安装，包含 Node 运行时、编译后的服务和 Angular 资源、托管启动器、注入脚本、Skill 源文件和卸载逻辑。目标机器使用安装版时不要求另行安装 Node.js。安装器创建新 Codex 快捷方式并保留官方原入口。

安装开始时显示程序目录选择器，默认父目录为 `%LOCALAPPDATA%`，最终程序根目录固定为用户所选父目录下的 `Feature Kanban` 子目录。该选择只影响应用、运行时、安装器副本、快捷方式目标和卸载注册项；业务数据及日志仍固定在 `%USERPROFILE%\.feature-kanban`，Skill 仍固定在 `%USERPROFILE%\.agents\skills\feature-lifecycle`。取消选择时不写入任何安装状态。已有安装更新时只允许沿用其已登记且身份校验通过的程序根目录；改变已有安装位置须先卸载，避免遗留或误删旧目录。

程序目录支持空格、中文和其他一般 Unicode，以及单引号、`&`、括号、方括号等 Windows 合法字符。实现必须使用规范化的绝对路径、literal 文件操作和结构化/正确转义的快捷方式与卸载参数，不通过字符串求值执行路径。复制任何应用文件、安装 Skill 或写注册表前，安装器校验：路径为本地固定磁盘上的非根目录、末级名称为 `Feature Kanban`、不与临时包目录互相包含、目标不存在或为空或具有匹配本产品和根目录的安装清单、目标不是重解析点、父目录可写，并且所有打包文件的最终路径处于 Windows PowerShell 5.1 可可靠处理的长度内。UNC/网络路径、非法字符、末尾空格或点、过长路径和含未知内容的既有目录均以明确错误安全停止。卸载器只有在相同的本地固定磁盘与路径约束以及安装清单身份同时成立时才递归删除程序根目录。

## 错误与恢复

- API 不可用：AI 在生命周期文档记录同步失败并继续；服务恢复后的下一次上报使用完整快照。
- POST 响应丢失：文档已持有 `cardId`，重试相同 POST 不产生重复卡片，也不回退服务端已有快照；调用方随后 PATCH 当前完整快照。
- 并发上报：服务接受最后到达的合法快照；历史会话不会因卡片快照覆盖而删除。
- SQLite 事务失败：请求失败且不发 SSE；客户端保留旧画面。
- SSE 断开：界面显示已有快照，重连后完整刷新，不创建卡片错误标记。
- 普通 Codex 已运行：启动器只显示关闭后重试的错误，不结束用户进程。
- 注入失败：服务可以继续独立运行；启动器明确报告失败并清理自己启动的 Codex/注入资源，不删除数据。
- 归档后继续执行：下一次成功 AI 上报自动取消归档。

## 验证策略与验收场景

生产实现完成后再添加风险相称的自动化行为测试，不采用 RED → GREEN。至少验证：

- 客户端生成 ID 的 POST 首次创建、响应丢失重试和身份冲突。
- PATCH 最后写入者覆盖、阶段与进度匹配校验、归档后自动恢复。
- 项目名聚合、`All`、AI 工具和归档筛选。
- 会话接管保留旧记录、活动会话唯一、匿名会话可继续更新。
- SQLite 事务失败不广播 SSE；SSE 事件只携带受影响卡片标识。
- Angular 合并相同卡片通知，只定向重拉一次，并且只在真实阶段变化时播放一次动画。
- 用户无法从 UI 改变阶段，任意阶段可归档。
- 生命周期 Skill 在 API 不可用时记录失败且不启动服务；恢复后沿用文档 ID。
- Windows 启动器的单实例、普通 Codex 冲突、服务所有权和 Codex 退出清理。
- 两个固定回环端口的合法服务复用、其他监听者占用报错及源码端口覆盖。
- 安装器的自选程序目录、空格/中文/符号路径、安全卸载身份校验，以及唯一 `.agents` Skill 目标的备份、无修改恢复和用户修改保护。

完整质量门禁应覆盖 TypeScript 类型检查、Angular 生产构建、服务与 UI 行为测试、Skill 静态检查、Windows 启动器测试以及安装包构建或等价的打包内容校验。当前仓库没有既有门禁，具体命令由实现计划基于生成的项目脚本确定。

## 变更面契约

### 交付目标与新增内容

本需求在空仓库中新增 Node.js/TypeScript 服务、SQLite schema、Angular 应用、Windows 启动器与安装器、Codex 注入层、跨工具 `feature-lifecycle` Skill、测试、构建配置和用户文档。

### 既有生产代码影响

仓库当前没有生产代码、Domain 模型、数据库、公共 API、事务、异常、补偿、权限或业务控制流。本需求不修改或删除任何既有生产文件。已有 `LICENSE` 和基础 `.gitignore` 保持不变。

### 已批准的外部与运行影响

- 新增一个无令牌、仅监听回环地址的本地 REST/SSE 服务；任何本机进程都能调用写 API。
- Windows 启动器以调试参数启动官方 Codex，在运行期间开放回环 CDP，并向渲染器注入侧边栏、iframe 与消息桥。
- 安装版默认占用回环 TCP `46171`（看板 REST/SSE）与 `46172`（Codex CDP）；端口已占用且不能合法复用时启动失败，不会接管或终止占用进程。
- 安装器在用户选择的本地父目录下创建 `Feature Kanban` 程序根目录，在用户目录写入 `.feature-kanban` 数据，只在用户级 `.agents\skills\feature-lifecycle` 安装或备份 Skill，并创建新的 Codex 快捷方式。
- 关闭托管 Codex 会停止启动器拥有的看板服务；手工服务不受影响。

这些影响均已在需求讨论中逐项披露并获得用户明确选择。

### 必须保持不变

- 不修改官方 Codex 可执行文件、安装包、原快捷方式、默认 profile 数据或私有数据文件。
- 不自动关闭用户从原入口启动的 Codex。
- 不由服务或 Skill 操作 Git/worktree。
- 不由 UI 修改生命周期阶段。
- 不把看板同步失败伪装成已成功上报。

### 资源与未验证项

运行时新增一个本地 Node 服务、一个 SQLite 文件、SSE 长连接和一个 CDP 监听端口。首版没有多人并发、远程网络或大规模数据目标，不执行跨设备、长期稳定性或高并发压测。Windows 安装包在具体打包工具确定后必须执行可构建性和内容校验；官方 Codex 版本变化可能影响 DOM 注入与路由桥，需要以当前安装版本做专项验证。

### 更低侵入替代方案

更低侵入方案是只提供浏览器中的 Angular 看板和手工安装 Skill，不启动或注入 Codex，也不创建新快捷方式。它可以保留 REST、SSE 和生命周期快照，但无法在 Codex 内查看看板、无法可靠跳回原生会话，也不能满足“启动 Codex 自动启动看板、关闭 Codex 自动关闭看板”的已确认需求，因此不采用。
